## 2. 三个方案取舍

### 方案 A：模型直接写 CQ 码
让模型在回复里写 `[CQ:image,file=xxx]`，桥接层原样透传。

- **优点**：改动最小（几乎零）。
- **否决理由**：模型会写错格式、会幻觉出不存在文件、无法约束频率；且官方机器人路径不支持 CQ 码。**不采用。**

### 方案 B：模型调用「发表情」工具
给模型一个 `send_sticker(name)` 工具，桥接层执行真实发送。

- **优点**：语义清晰，可校验名字是否存在。
- **问题**：QQ 主会话当前是 **0 tools** 设计（见 dsh-companion-memory README：
  「主会话屏蔽运行上下文」「主会话 0 tools」）。加工具会破坏这个前提——
  实测过，只要请求里存在 `tools` 字段，模型的 thinking 就会被拉进
  function-calling 规划模式，角色独白退化。**这是硬约束，不能碰。**

### 方案 C：正文标签（推荐）
沿用已有的咒语/控制块模式，模型在正文里写标签，桥接层剥离并执行。

- **优点**：与现有 `<读取>`/`<改写>` 架构一致；主会话仍然 0 tools；可校验、可限流。
- **与已有机制的关系**：现有机制已经证明这条路可行——bridge 已经在剥离
  「闭合的中文咒语标签」，出站可见文字不含标签。

**结论：采用方案 C。**

## 3. 表情包存储设计

### 3.1 位置

```
<DSH home>/plugins/dsh-qq-bridge/<账号命名空间>/stickers/
├── index.json          # 索引:名字 → 元数据
└── <sha256 前 16>.<ext> # 内容寻址的图片本体
```

理由：与 `delivery.json` 同命名空间，天然按 QQ 账号隔离（多号场景各自独立）；
不在仓库里，不进 Git。

### 3.2 索引结构

```json
{
  "schema": 1,
  "stickers": {
    "委屈": {
      "id": "a1b2c3d4e5f60718",
      "mediaType": "image/gif",
      "bytes": 48213,
      "width": 240,
      "height": 240,
      "addedAt": "2026-10-27T16:00:00Z",
      "source": "user",
      "uses": 7,
      "lastUsedAt": "2026-10-27T17:20:00Z",
      "description": "低着头的猫耳少女，眼含水光"
    }
  }
}
```

关键字段说明：

- `id`：内容 sha256 前 16 位，去重靠它；同一张图存两次只有一个文件。
- `description`：**必须有**。没有描述的图模型无法在正确语境选用，
  只会变成随机发表情。见 §3.3。
- `uses`/`lastUsedAt`：用于限流与「最近没发过」判断。

### 3.3 描述从哪来（关键设计）

模型只能在**文字层面**理解表情包，所以描述质量决定可用性。三个来源：

1. **用户添加时手写**（最可靠）：`/存表情 委屈 <描述>` + 直接发图。
2. **模型看图生成**（入站读图已具备）：用户发图时模型能看图，可提议描述。
   这正好衔接刚完成的入站能力。
3. **复用记忆系统**：把表情包描述存成 companion-memory 的一条事实，
   让召回自然带出「主人喜欢这张委屈脸」。**推荐**，见 §5。

## 4. 标签协议设计

### 4.1 标签形态

沿用现有中文尖括号风格，与 `<读取>`/`<改写>` 一致：

```
<表情>委屈</表情>
```

规则：

- 只认英文冒号无关的纯名字，长度 1–8 个中文字符（与咒语名字规则一致）。
- **未闭合标签不剥离**（与现有咒语规则一致，防止误伤）。
- 名字不存在时：桥接层静默丢弃该标签，不打断回复，不向用户报错
  （报错会让对话变得机械）。但写日志，便于发现模型幻觉。

### 4.2 与文字混排

模型可以这样输出：

```
主人今天好辛苦呢……（蹭蹭）
<表情>抱抱</表情>
早点休息哦。
```

桥接层拆成三段：文字 → 图片 → 文字。这要求出站从「发一条字符串」
变成「发一串有序段」。这是本方案**唯一有侵入性的改动**。

### 4.3 频率约束

| 约束 | 值 | 理由 |
|---|---|---|
| 单轮最多几张 | 2 | 多了像刷屏 |
| 连续几轮都发则抑制 | 3 | 防止每轮必发 |
| 同一张冷却 | 20 轮 | 防止复读 |

超出时静默丢弃并记日志。不向模型回报——回报会诱导它继续尝试。

## 5. 与记忆系统的关系（推荐做法）

不要在 bridge 里建一套独立的「表情包知识」，**而是复用已有权威**：

```
companion-memory (权威)
  ├── 事实: "主人喜欢这张委屈猫猫脸"
  ├── 事实: "拍头表情用于安慰场景"
  └── 表情包索引: 只在 bridge 本地存文件与 id
```

理由：

1. 你已经有更正/删除/屏障机制。用户说「别再发这个表情」应当能真的生效，
   而这正是记忆服务已经解决的问题。
2. 表情包的**文件名**是二义的，**记忆里的描述**才是可召回、可更正的语义。
3. 避免两套会各自漂移的「用户偏好」真相。

落地方式：表情包文件留在 bridge 本地（二进制不适合进记忆），
**描述与使用偏好存 companion-memory**，通过已有的
`memory_tools` 授权写入。模型发送时读索引拿 id，读记忆判断语境是否合适。

## 6. 实施拆分

| # | 工作项 | 侵入性 | 可独立验收 |
|---|---|---|---|
| S1 | 表情包索引 + 存储（`stickers/`、`index.json`、增删查） | 低 | ✅ 单测 |
| S2 | `/存表情` 控制指令：收图 + 描述 + 存库 | 低 | ✅ 手动 |
| S3 | 标签解析 `<表情>名</表情>` + 剥离 | 中 | ✅ 单测 |
| S4 | 出站分段：文字/图片混排发送 | **高** | ✅ 单测 + 实机 |
| S5 | 频率约束与冷却 | 低 | ✅ 单测 |
| S6 | 与 companion-memory 的描述联动 | 中 | 需记忆服务在 |

**S4 是唯一会动到现有发送链路的改动**，建议最后做，且先只支持
「一轮一条图片段」的最小形态，验证通过再扩展混排。

## 7. 风险

| 风险 | 影响 | 对策 |
|---|---|---|
| 模型滥用标签刷屏 | 体验破坏 | 频率约束；超限静默 |
| 模型幻觉不存在的名字 | 静默失败 | 丢弃 + 日志计数；索引名可注入提示 |
| 出站分段改动破坏现有文字路径 | **回归风险最高** | S4 最后做；现有 216 项测试作护栏 |
| Windows 与 Linux 路径差异 | 部署问题 | 沿用现有 `join()`，不拼字符串 |
| 服务器 PNG 体积 | 传输/存储 | 入站已限 10MB；存储侧建议统一转 WebP（记忆管理台已有先例，10MB→1.35MB） |

---

## 8. 不做什么

- **不做表情包自动抓取**：从聊天里自动收集所有图片会迅速变成垃圾场，
  且涉及他人图片的使用权。
- **不做表情包市场/下载**：超出插件边界。
- **不改主会话 0-tools 设计**：这是实测得出的硬约束。
- **不在 bridge 新建用户偏好存储**：复用记忆服务。

## 9. 待确认问题

1. **表情包名字用中文还是英文？** 现有咒语用中文，建议沿用中文以保持一致。
2. **是否需要「随机发一张某类表情」？** 例如 `<表情>随机:开心</表情>`。
   能力更强但更难约束，建议先不做。
3. **S4 是否接受「图片单独成条」**（不与文字混排）？这会显著降低改动风险：
   仍发多条消息，只是某一条是图片段。**推荐先这样。**
